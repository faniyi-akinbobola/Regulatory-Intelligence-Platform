Sessions
Sessions have two different meanings here and you need to decide:

Meaning 1 — Request-scoped session (what you need for MVP):
Every call to /analyze-business generates a new session_id (UUID). It's passed through the workflow, stored in the audit record, and returned to the caller. That's it. No Redis needed. The caller uses the session_id to retrieve the audit trace via GET /audit-trace/{id}.

Meaning 2 — Persistent conversation session (future, chat interface):
A user has an ongoing session where follow-up queries build on previous analysis context. This requires Redis to cache the session state (prior analyses, organization context, conversation history) and a POST /sessions endpoint to create sessions explicitly. The session_id is created once and reused across multiple /analyze-business calls.

For your MVP: implement Meaning 1 only. The /analyze-business request body includes an optional session_id field. If not provided, one is generated. This lets the caller chain analyses manually if needed without requiring a full session management system. Redis stays dormant for now.
